## 1. Critical

### C1. Default credentials ship enabled, and the UI fills them in for you
- `backend/app/core/config.py:33-37`: JWT secret defaults to `"veritas-secret-key-change-me-in-production"`, admin to `admin/admin`. Nothing refuses to start with these defaults. Only `docker-compose.yml` forces them to be set.
- `backend/app/models/database.py:367`: on every start it seeds a `user / user123` account when one is missing. Deleting it does not help because it comes back on the next restart.
- `frontend/src/pages/AdminLoginPage.jsx:44-45,176` and `LoginPage.jsx:45,158`: buttons that fill in `admin/admin` and `user/user123`.
- `core/security.py authenticate_user` also accepts the env admin credentials directly, even after the DB has users, so rotating the admin password in the DB does not lock out `admin/admin`.
- **Impact:** anyone who knows the default secret can forge admin JWTs, and anyone can log in as admin on a non-compose deploy.
- **Fix:** fail at startup if the secret or password is unset or equals a default. Remove the seeded `user` and the env-credential fallback. Delete the fill-in buttons, or gate them behind `import.meta.env.DEV`.

### C2. The detector has no measured efficacy on its own benchmark
`backend/research/results/2026-09-02-benchmark-v1-eval-r3.json` at the shipping 0.35 threshold: precision, recall and F1 are **0.0 for every layer and for the combined score**. Only Layer-3 row-level recall is non-zero (backdoor 0.20, gradient 0.08, boiling-frog 0.48). `pipeline.py:61-66` says this itself in a comment. Meanwhile the README and UI still advertise "5-layer detection", "Attack type classification", "Grade A–F" trust scores and "CONFIRMED_POISONED" verdicts.
- **Impact:** a user will get confident-looking verdicts that the project's own evaluation does not support.
- **Fix:** put the benchmark numbers on the dashboard and README, and label verdicts "experimental". Otherwise drop the combined verdict until recall > 0.

### C3. Data cleaning removes the signals the detector looks for
`backend/app/ingestion/csv_engine.py`
- `:184` drops exact duplicate rows. Duplicated injected samples are a classic poisoning pattern, and Layer 3 even has a near-duplicate signal, which never sees them.
- `:228-229` clips every value to 5×IQR. Spike or trigger values get flattened before L1/L2 run.
- `:339` normalises min/max over the **whole** file, so incoming rows shape the reference scale.
- **Fix:** run detection on raw (only coerced and imputed) data. Report duplicates and outliers as findings instead of deleting them.

### C4. Ground-truth poison columns are used as the training label
`csv_engine.py:45`: `poisoned`, `is_poisoned`, `attack`, `anomaly`, `prediction` are on the priority list of label names **[verified: a CSV with `is_poisoned` gets it chosen as the label]**. The supervised layers (L4 causal, SHAP drift) then train on the answer key.
- **Fix:** treat those names as ground-truth or evaluation columns. Exclude them from features and labels, and if present use them only to score the detector.

## 2. High

### H1. Model scanner can't load most of its advertised models **[verified]**
`ingestion/model_engine.py` `SAFE_GLOBALS` doesn't include `sklearn.tree._tree.Tree` or `sklearn.preprocessing._label.LabelBinarizer`, so these fail:

| Model | Result |
|---|---|
| LogisticRegression | OK |
| DecisionTree / RandomForest / ExtraTrees / GradientBoosting / AdaBoost / Bagging | **FAIL** `Disallowed pickle global: sklearn.tree._tree.Tree` |
| MLPClassifier | **FAIL** `LabelBinarizer` |

The restricted unpickler itself is a good design. Add the specific classes, each with a regression fixture (the code comment already asks for this).
Also: `:150` uses an unseeded `np.random.choice`, so scanning the same model twice gives different results. Seed it.

### H2. Global mutable pipeline shared across requests (race conditions)
`api/routes/datasets.py:67, 142, 252` call `deps.pipeline.fit_baseline(...)` on the one module-level `DetectionPipeline`, and the red-team simulator is pointed at it. Concurrent `/demo/run`, `/detect/analyze` and `/redteam/simulate` overwrite each other's baselines.
The same applies to `deps.defense` (a global cooldown: one user's quarantine silences auto-defense for everyone) and to the singletons in `dependencies.py`.
- **Fix:** build a fresh `DetectionPipeline()` per request, as the upload path already does.

### H3. CPU-heavy work blocks the event loop
`/detect/analyze` (`datasets.py:131`) and `/redteam/simulate` run the full pipeline, including the 100-bootstrap causal layer, **synchronously inside `async def`**, which freezes the whole server, including WebSockets and health checks. `/detect/analyze` also has no rate limit.

### H4. Analysis latency doesn't fit a synchronous HTTP request **[verified]**
Clean random data, 10 features: **2k rows → 21 s, 20k rows → 85 s**. The advertised limit is 200k rows. The main cost is `layer4_causal._bootstrap`: 100 × 3-fold CV.
- nginx has no `proxy_read_timeout` (default 60 s), so 20k-row uploads already return 504 in Docker.
- `app/jobs/queue.py` and `/jobs/{id}` already exist but **nothing submits jobs**. Wire uploads through it (return `job_id`, poll), or cut the bootstrap count.

### H5. Docker uploads are capped at 1 MB
`frontend/nginx.conf` has no `client_max_body_size`, so nginx's 1 MB default applies. The backend allows 200 MB and the README promises 200 MB. Set `client_max_body_size 200m;`.

### H6. Behind nginx, all rate limits key on the proxy IP
uvicorn runs without `--proxy-headers --forwarded-allow-ips`, so `request.client.host` is always the nginx container. The login limiter (5/min per IP) becomes **5 failed logins per minute for the whole site**, which lets anyone lock out every user.

### H7. No tenant isolation on results
All results are global. Any authenticated user can read any other user's upload through `/analyze/upload/latest`, `/analyze/upload/{id}`, `/history/{id}`, `/forensics/latest`, `/reports/generate`, `/analyze/model/{id}` and `/jobs/{id}`. WebSocket broadcasts send every user's verdicts to every connected client. Acceptable for a single-team demo, but it should be written down. Add an `owner_id` column and filter on it if more than one team will use this.

### H8. "Defense" actions are cosmetic or act on the wrong data
- `routes/reports.py:166` `POST /defense/quarantine` quarantines `get_demo_data()["samples"][:50]`, **synthetic demo rows**, whatever the analyst is looking at.
- `quarantined_ids` lives only in memory and is lost on restart. Nothing outside that set changes.
- HITL `decide` (`reports.py:189`) takes `reviewer` from the request body (spoofable, so take it from the JWT), returns `{"error": ...}` with HTTP 200, isn't audit-logged, and `approve_quarantine` does nothing.
- HITL cases are only ever queued from `/demo/run`. Real uploads never reach the review queue.
- Red-team `false_positive_rate` is hard-coded to `0.0`.

## 5. What's good
- The restricted unpickler is the right approach (allow-list globals before construction), and it has tests.
- Parameterised SQL everywhere. No string-built queries.
- bcrypt hashing, `compare_digest` on the env login, JWT claim validation, admin-only router dependency.
- Bounded chunked upload reads. Shared thread pool for the upload path. Request IDs in error messages.
- The benchmark harness (`research/`) is honest and pre-registered, and that is how C2 came to light.
- The "honest empty states" work (no fake Grade A when there is no data).
